| Layer | Choice | Notes |
|---|---|---|
| Language | Python 3.12+ | strict typing throughout (`mypy --strict` target) |

**Router/service split rule:** routers never touch the Gel client directly — they call a
service function and pass/return Pydantic models. Services never know about `Request`,
`Response`, or Jinja — they return plain typed data. This keeps both layers independently
testable.

## 3. Feature Breakdown

### 3.1 Authentication (multi-user, secure)
- Register (username/email + password), password hashed with `argon2-cffi`.
- Login sets a signed, HTTP-only session cookie (e.g. `itsdangerous` signed token or a
  server-side session row in Gel keyed by a random token — leaning towards the latter
  for easy revocation/logout-everywhere).
- `deps.get_current_user` dependency used on every protected router to load the user
  from the session and 401/redirect to `/login` if absent.
- All collection data is scoped to `user.id` — no cross-user data leakage.

### 3.2 Sticker catalogue
- The 992 stickers (per Section 0) are static reference data, seeded once via
  `scripts/seed_catalogue.py` into a `Sticker` type (id/code/team/kind).
- `sticker_service.py` exposes `list_all_stickers()`, grouped by team/section for
  rendering the checklist grid in the right order (00 → FWC → CC → each team A–Z or by
  group, TBC with you).

### 3.3 Checklist view (main interface)
- Grid of all 992 stickers, grouped by section/team.
- Each sticker cell is a clickable/tappable element:
  - **Not owned** → grey/black
  - **Owned (qty 1)** → green
  - **Owned (qty 2+)** → green + a duplicate badge/count
- Clicking a grey sticker → marks owned (qty 1).
- Clicking an already-green sticker → increments to duplicate (qty 2+), which also adds/
  updates an entry in the Duplicates view.
- Toggle is a small fetch/HTMX call to a router endpoint that updates state and returns
  the re-rendered `_sticker_grid.html` fragment (or just the single cell) — no full page
  reload.

### 3.4 Duplicates view
- Lists every sticker the user owns with quantity ≥ 2, with a "remove one" action
  (representing trading it away) that decrements the quantity — down to 1 removes it
  from the duplicates list but keeps the sticker itself green/owned.

### 3.5 Progress summary
- Simple counter: e.g. "612 / 992 collected, 34 duplicates" — nice-to-have on the
  checklist page header.

### 3.6 Undo / Edit mode (new requirement)
Accidental taps need to be reversible. Since the primary interaction (single tap) is
one-directional (grey → owned → duplicate, increasing quantity), a secondary **Edit
mode** toggle will be added to the checklist view:

- A toggle button/switch in the page header switches the grid into "Edit mode."
- While in Edit mode, tapping a sticker **decrements** instead of increments:
  - duplicate (qty ≥ 2) → owned (qty 1)
  - owned (qty 1) → not owned (qty 0) — the underlying `CollectionEntry` row is deleted
    to stay consistent with the lazy-creation approach, rather than kept at 0.
  - not owned (qty 0) → no-op (nothing to undo).
- Edit mode is a pure UI/client-state toggle (no server round-trip to switch it) — it
  just changes which `collection_service` function the tap's HTMX request calls
  (`increment_sticker` vs `decrement_sticker`).
- `collection_service.decrement_sticker()` is the counterpart to the existing
  increment logic and is symmetric: it never goes below 0, and removing the last
  unit deletes the row.
- Since this is expected to be lightly used, no confirmation dialog is planned by
  default — happy to add a "tap and hold" or confirm-on-decrement-to-zero step if you'd
  prefer extra friction there.

## 4. Proposed Gel (EdgeDB) Schema — NOT YET MIGRATED

```sdl
module default {
    type User {
        required username: str {
            constraint exclusive;
        }
        required email: str {
            constraint exclusive;
        }
        required password_hash: str;
        required created_at: datetime {
            default := datetime_current();
        }
        multi link collection_entries := .<user[is CollectionEntry];
    }

    type Session {
        required token: str {
            constraint exclusive;
        }
        required user: User;
        required created_at: datetime {
            default := datetime_current();
        }
        required expires_at: datetime;
    }

    scalar type StickerKind extending enum<Special, Generic, Promo, Team>;

    type Sticker {
        required code: str {
            constraint exclusive;   # e.g. "MEX7", "FWC3", "CC12", "00"
        }
        required kind: StickerKind;
        team_code: str;             # null for Special/Generic/Promo
        required sort_order: int32; # for deterministic grid rendering
    }

    type CollectionEntry {
        required user: User;
        required sticker: Sticker;
        required quantity: int16 {
            default := 0;
            constraint min_value(0);
        }
        constraint exclusive on ((.user, .sticker));
    }
}
```

Notes / open questions for you before this is migrated:
- `quantity = 0` effectively means "not owned" — do you want entries created lazily
  (only when first marked owned) or pre-created for every user × every sticker (992 rows
  per user)? Lazy creation is leaner; I'd lean that way unless you disagree.
- `Session` as a DB type enables "log out everywhere" and inspection, at the cost of a
  DB hit per request — alternative is a signed stateless cookie. Happy to go either way.
- Do you want duplicate *counts* (quantity int) or duplicate *individual rows* (in case
  you want to track e.g. condition/notes per duplicate)? Plan currently assumes a count.

**I will not run `gel migration create` / `gel migration apply` until you confirm this
schema (or an amended version) explicitly.**

## 5. Frontend Plan

- `templates/base.html`: `<html>` shell, Tailwind stylesheet link, nav bar (Checklist /
  Duplicates / Logout), a `{% block content %}`.
- Each route has its own template extending `base.html`, plus a `_fragment.html` used
  for partial re-renders on interaction (sticker toggle, duplicate removal) so we avoid
  a heavy JS framework — plain `fetch()` calls swapping `innerHTML`, or HTMX if you're
  happy pulling that in (recommend HTMX — trivial footprint, works great with Jinja
  fragments and avoids hand-rolled fetch/DOM code).
- Tailwind compiled via the Tailwind CLI (`npx @tailwindcss/cli` or standalone binary) —
  will confirm exact setup when we get there since it's a Node-side step, not `uv`.
- Colour system: `bg-gray-800` (not owned) / `bg-green-500` (owned) / `bg-green-600` +
  badge (duplicate), all as Tailwind utility classes driven by a `status` value passed
  from the router into the template.

## 6. Testing Strategy

- **Services** tested directly with a real (test) Gel instance/branch — no HTTP
  involved. E.g. `test_collection_service.py` verifies marking owned, incrementing to
  duplicate, decrementing, and that data is scoped per-user.
- **Routers** tested via `httpx.AsyncClient` against the FastAPI app with a logged-in
  test session fixture — verifying status codes, template rendering, and auth
  protection (401/redirect when not logged in).
- `conftest.py` will spin up/tear down a dedicated test Gel branch/database per test
  session, seeded with the sticker catalogue fixture data, so tests never touch real
  user data.
- Target: every service function and every router endpoint has at least one happy-path
  and one failure-path test before being considered "done."
